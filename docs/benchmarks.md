# Первые замеры (16.10.2026)

Условия: облачный сервер, Intel Xeon 2,1 ГГц, g++ 13, сборка Release (`-O3`), минимум из двух прогонов `bench`. На виртуальной машине разброс между прогонами доходит до ±20%, поэтому смотрите на порядки и соотношения, а не на точные цифры. У вас на ноутбуке цифры будут другими.

Повторить: `./build/bench` → таблица в консоли и `bench_results.csv`.

## Выводы

1. **Время съедает длинная арифметика, а не комбинаторика.** При n = 10 000 код Лемера считается за 0,2 мс, а его перевод в число — около 13 мс, то есть примерно 98% времени. При n = 30 000 — больше 99%.
2. **«O(n log n)» на практике растёт квадратично.** n больше в 3 раза (10 000 → 30 000) — время rank больше примерно в 9 раз. У сочетаний n больше в 10 раз — время больше примерно в 100 раз. Причина: каждая из ~n операций проходит по всему числу длиной ~n log₂ n бит.
3. **Myrvold–Ruskey «O(n)» не обгоняет лексикографический O(n log n)** по той же причине: комбинаторная часть и так дешёвая.
4. **select на больших n медленнее rank в 8–10 раз:** деление длинного числа на короткое заметно дороже умножения.
5. **Наивный O(n²) проигрывает Фенвику** в rank (0,16 с против 13 мс при n = 10 000), а в select разницы почти нет: там всё равно доминирует деление.

**Что из этого следует для проекта.** Главный резерв ускорения на больших n — перевод между «цифрами» и длинным числом. Кандидаты: «разделяй и властвуй» (дерево произведений) с умножением Карацубы вместо n проходов по числу; упаковка нескольких маленьких множителей в один 32-битный; готовая библиотека GMP для сравнения. Это и есть «эффективная программная реализация» из названия темы, и хорошая иллюстрация «теория против практики» для отчёта.
